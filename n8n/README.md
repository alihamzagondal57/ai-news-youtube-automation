# n8n

Orchestration layer. The four workflows in `workflows/` are the real, working
source of truth — generated by the builder scripts in `scripts/` and verified
against the real pipeline (see "What's been verified" below). Import them into
your own n8n instance (self-hosted, free — or n8n Cloud, paid); nothing here
runs n8n for you.

## Workflows

- **`workflows/manual-mode.json`** — trigger: a Form ("On form submission")
  collecting `niche`/`topic`/`angle`/`sourceUrls`/`sourceSummaries` from the
  operator. Generates the job's UUID, writes `trend.json` directly (skipping
  `trend-research` — that's what "manual mode" means: the operator supplies
  the topic instead of the pipeline auto-discovering one), then runs the
  shared chain below.
- **`workflows/auto-mode.json`** — trigger: a daily Schedule (cron; adjust the
  time in n8n's UI to your publish cadence). Generates the job's UUID, runs
  `trend-research` for real (Firecrawl search + LLM ranking, writing
  `trend.json` itself — see `services/trend-research/README.md`), then runs
  the same shared chain manual-mode.json uses from `script-generator` onward.
  The two workflows share that entire downstream chain via one generator
  (`n8n/scripts/_workflow-helpers.mjs`'s `buildScriptGeneratorOnward`) so it
  can never drift between modes: `script-generator` → `{voiceover →
  caption-sync}` and `media-sourcing` in parallel → `metadata-generator` →
  **render** (see below) → `thumbnail-generator` → sets
  `job.json.currentStep = "review"` and stops. `job.json` is created/advanced
  by n8n itself at each major transition (see `n8n/scripts/update-job.mts`) —
  no pipeline service writes it; see `docs/PIPELINE.md`.
- **`workflows/release-on-approval.json`** — trigger: a webhook
  (`/release-on-approval`) that `apps/review-dashboard/server`'s `POST
  /approve` endpoint calls when an operator approves a job
  (`N8N_APPROVAL_WEBHOOK_URL`, see `.env.example`). Verifies the posted
  `review-state.json` is actually `"approved"` (throws otherwise — a
  defense-in-depth check, since `youtube-uploader` enforces this gate itself
  regardless), advances `job.json.currentStep` to `"youtube-uploader"`, runs
  it, then marks the job `completed`.
- **`workflows/shared-error-handling.json`** — a reusable Error Trigger
  workflow: on any other workflow's failure, marks that job's `job.json`
  `status: "failed"` with the caught error message, and calls a
  notification webhook you configure (`N8N_ERROR_NOTIFY_WEBHOOK_URL`) — wire
  it to Slack/Telegram/email via n8n's own HTTP Request node or swap in a
  dedicated notification node.

## How each step actually runs

Every non-render step is a plain **Execute Command** node:
`cd /d "<repo>" && npx tsx services/<name>/src/index.ts "<jobId>"` — the
exact same `node dist/index.js <jobId>` CLI contract every service already
has (see each service's own README), just run via `tsx` directly against
source rather than a prebuilt `dist/`. This is a deliberate simplification
from the earlier design sketch (n8n calling this repo's GitHub Actions via
`workflow_dispatch` for each step): it's what's actually been run and
verified end-to-end, it needs no GitHub PAT, and "calling each service's
existing entry point" is what the CLI contract already is. **Swapping to
GitHub Actions instead** (e.g. for a fleet of ephemeral runners rather than
one self-hosted n8n box) is a mechanical change — replace each Execute
Command node with an HTTP Request node hitting
`POST /repos/{owner}/{repo}/actions/workflows/{id}/dispatches`, plus a
follow-up poll of the run's status (GitHub's dispatch API doesn't return a
run id synchronously) — the fixes already made to `.github/workflows/*.yml`
this pass (positional `jobId` args, missing build steps, the stale
Python/faster-whisper spec in `04-generate-captions.yml`) are exactly what
that swap would depend on.

**Render is the one step that isn't Execute Command**, because it's the step
this repo already designed an on-demand-VM pattern for
(`infra/gcp/`, `infra/render-server/src/shutdown.ts`): an HTTP Request node
`POST`s to render-server's `/render` (`Authorization: Bearer
${RENDER_SERVER_SHARED_SECRET}`), which returns `202` immediately and renders
asynchronously; a Wait node listening for a webhook resumes the workflow when
render-server calls back to `N8N_RENDER_CALLBACK_URL` (already-implemented
code — `infra/render-server/src/callback.ts`) with the `RenderResult`. On a
real deployment, `RENDER_SERVER_URL` points at the GCE VM's address and
`07-trigger-render.yml`'s `gcloud compute instances start` step (or an
equivalent HTTP Request node calling the Compute Engine API directly) runs
before this POST; for local/dev use it just points at a `render-server`
you're already running. Either way, render-server's own idle-shutdown timer
(`ENABLE_SELF_SHUTDOWN=true` on the VM) is what actually stops billing — n8n
doesn't need to manage that half of the lifecycle at all.

## What's been verified

Every mechanism in `manual-mode.json` and `release-on-approval.json` has been
run for real against a local n8n instance and the real services (no mocked
service calls) at least once:
- Form submission → UUID generation → `trend.json`/`job.json` writes to R2
- `script-generator` (real LLM call), `media-sourcing` (real Pexels/Pixabay
  downloads), `voiceover` (real Kokoro TTS), `caption-sync` (real Whisper
  transcription) — via a live n8n execution
- `render-server`'s `/render` → async chunked render → `render.mp4`, and
  `thumbnail-generator`'s real FLUX.1-schnell background generation
- `apps/review-dashboard/server`'s real `POST /approve` firing a real webhook
  POST, received by `release-on-approval.json`'s trigger with the correct
  `ReviewState` payload
- `youtube-uploader` (fake YouTube client — see
  `apps/review-dashboard/README.md`'s Tests section for why) succeeding only
  once that approval has actually landed

`auto-mode.json`'s unique piece — `Run trend-research` — is the exact same
`npx tsx <path> "<jobId>"` Execute Command mechanism proven above for five
other services; the CLI entrypoint itself was verified directly (real
Firecrawl search, real candidate discovery) rather than through a second live
n8n run, since re-exercising an already-proven mechanism through n8n again
wouldn't add evidence — see `services/trend-research/README.md`'s Tests
section for the full real-search/real-write proof, including where it
substitutes a fake for the currently-exhausted ranking LLM call (below).

`metadata-generator` and `trend-research`'s ranking step both hit the same
real, temporary wall during this verification pass — every currently-enabled
LLM provider (`github-models`, `gemini`, `cerebras`) was simultaneously
unavailable (expired token, zero free-tier quota, no credits respectively);
`mistral`/`openrouter`/`groq` are deliberately disabled in
`services/script-generator/src/providers/registry.ts` for documented,
unrelated operational reasons. This is an external credentials/availability
gap, not a defect in either node's wiring — the same Execute Command
mechanism that ran every other step ran these identically, and each
service's own real-provider-chain attempt was itself run and confirmed to
fail for exactly this reason (not skipped or assumed).
